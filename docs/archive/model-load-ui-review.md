# 模型加载页界面评审（ModelLoadPage）

评审范围：`app/src/pages/ModelLoadPage.tsx`、`app/src/features/model/ModelWorkspace.tsx`、`app/src/index.css`
目标窗口：1440 ~ 1600 宽（桌面端，左侧栏 240px 常驻）
痛点对应：信息层级不清 / 留白与密度失衡 / 操作动线绕

---

## 0. 现状速览

当前页面自上而下是四层东西，全部平铺在一个 `sticky` 顶栏里加一串折叠区：

| 位置 | 实际内容 | 频率 | 视觉权重（现状） |
|---|---|---|---|
| 顶栏第 1 段 | 头像 + 模型名 + API 名输入框 + params/quant/体积/MoE 标签 | 常看 | 中 |
| 顶栏第 2 段 | 预计显存总预测 + 6 个分项 pills | 常看 | 中 |
| 顶栏第 3 段 | tab 切换 + 自动调参 + 重置 + 加载模型 + 停止 | 高频 | 高（含主色按钮） |
| 顶栏第 4 段 | 进度文案 + 百分比 + 进度条 + 缺表头警告 | 高频 | 低 |
| 正文第 1 块 | 运行记录 / 调参日志 | 低频（排障） | 中（默认折叠但占位） |
| 正文第 2 块 | 推理与显存 \| 缓存与运行行为（两列） | 高频 | 中 |
| 正文第 3 块 | 高级参数（折叠） | 低频 | 低 |

## 1. 信息层级梳理

### 1.1 应该分成的三层

| 层级 | 内容 | 判定标准 |
|---|---|---|
| **L1 决策层** | 模型身份、显存结论、主行动按钮 | 用户每次进页面 3 秒内要看的东西 |
| **L2 诊断层** | 分项预测、加载进度、错误、缺表头警告 | 决策时用来验证的证据 |
| **L3 调节层** | 全部参数控件、模型元信息、日志 | 需要时才动的低频内容 |

### 1.2 问题 1：L1 与 L3 的控件混在同一个按钮组里（信息层级不清）

**现状**：顶栏第 3 段是一个 `flex-wrap` 容器，里面依次是 tab 切换器、`自动调参`、`重置`、`加载模型`，加载中再追加 `停止`。

tab 切换器的外壳是 `rounded-lg border + bg-[var(--app-bg)] + p-1`（`ModelLoadPage.tsx:1263`），`自动调参` 和 `重置` 是 `border + bg-[var(--surface)]`，`加载模型` 是 `bg-[var(--accent)]`。三者的形状、边框、内边距几乎一致，只是底色不同。

**为什么是问题**：tab 切换器是「看哪一块内容」，另外三个是「执行一个动作」。它们并排且同样式，用户必须逐个读文字才能判断哪个是导航、哪个是操作，破坏了"控件外观即语义"的惯例。

**调整**：tab 切换器从动作组里拿出来，下沉到状态行（与进度条同行）。动作组只剩三个真正的动作：`自动调参` / `重置` / `加载模型`。

**理由**：动作组里每剩一个按钮，它的位置语义就越清晰——从右往左是「主行动 → 次行动 → 危险操作」。导航不该占这个序列的名额。

---

### 1.3 问题 2：结论与推导过程同权重（信息层级不清）

**现状**：`预计 GPU 显存 11.42 GB` 是唯一带 16px 半粗体主色的大数字，右侧紧跟 6 个 `PredictionPill`（`ModelLoadPage.tsx:1252-1259`），pill 的值是 11px 半粗体，两者挤在同一 `grid-template-columns: auto minmax(0, 1fr)` 里（`index.css:460`）。

**为什么是问题**：总预测是用户做「能不能装下、要不要减 ctx」的唯一结论；6 个 pill 是这个结论的推导明细。默认状态下 7 个数字等权呈现，用户第一眼看到的是一串小数而不是那个大数。

**调整**：pills 独立成 L2 行，且默认收起为一行摘要（`权重 9.8 · KV 0.9 · 计算 0.4 · 运行 0.3`），点击「明细」展开为网格。

**理由**：分项预测的唯一用途是回答「显存超了，是权重还是 KV 导致的」。这是一个追问动作，不该占据默认视野。而且拆成独立行后，容器宽度要求从 1340 降到 1120（见第 3 节）。

---

### 1.4 问题 3：低频输入框的视觉重量超过模型名（信息层级不清）

**现状**：模型名是 `h1 text-sm font-semibold`（14px），紧邻的 API 调用名输入框是 `h-7 w-44 flex-grow border bg-[var(--surface)]`（28px 高、176px 起步、可继续增长），`ModelLoadPage.tsx:1203-1214`。

**为什么是问题**：API 调用名只在需要给外部客户端起别名时才改，频率极低；但它有边框、有底色、可增长，在视觉上比模型名更"实"。而模型名可能因为长被 `truncate` 截断，让位给输入框。

**调整**：输入框改为无边框 ghost 样式（仅 `focus` 时显边框），宽度收到 `w-36` 且不 `flex-grow`；模型名改为 `text-base font-semibold` 且允许占据剩余空间。

**理由**：模型名是这页的身份标识，API 名是附属元数据。视觉重量必须与重要性一致，否则用户每次进页面第一眼看到的重点会偏。

---

### 1.5 问题 4：进度条常驻显示 0%（信息层级不清）

**现状**：顶栏第 4 段永远渲染，文案在没有加载任务时回落到「显存预测会随参数实时更新」，百分比恒为 `0%`，进度条宽度 0（`ModelLoadPage.tsx:1333-1344`）。

**为什么是问题**：一根永远为 0 的进度条 + 一个 0% 数字，占了约 36px 常驻高度，但承载的信息量是零。它还让"正在加载"这个真正需要被注意的状态失去对比——因为未加载状态也长得像加载中。

**调整**：未加载时不渲染进度条与百分比，只在 `isLoading || loadError || 状态消息存在` 时出现。空闲态这一行改放当前参数摘要（如 `ctx 32K · ngl 45 · KV f16`），与 pills 同属 L2 行。

**理由**：空闲期的高度应该给"当前配置是什么"，而不是给一个 0。

## 2. 区块分布与留白

### 2.1 问题 5：区块顺序把排障信息放在了首屏第一位（操作动线 + 层级）

**现状**：正文第一个区块是 `RunRecordsCard`（`ModelLoadPage.tsx:539`），下面是参数区。它只在有记录时出现（`:951` 早退），所以首次使用看不到，但**从第二次起它就常驻在参数上方**。

**为什么是问题**：运行记录是"上次发生了什么"，是回溯信息；参数区是"现在要改什么"。每次进页面第一个看到的是回溯信息，把真正要调的参数往下推了一屏。

**调整**：把运行记录移到页面最末（高级参数之后），保持默认折叠但加一个"有 N 条新记录"的角标提示。

**理由**：首屏位置是稀缺资源，应该给最高频动作的入口。回溯信息"在那里"就够了，不需要"第一个看到"。

---

### 2.2 问题 6：区块之间零间距，全靠 1px 边框分隔（留白）

**现状**：一级区块之间只有 `border-b border-[var(--border-subtle)]`，没有纵向间距（`ParamSection` `:1065`、`RunRecordsCard` `:953`、高级参数折叠头 `:638`）。各块内边距也不统一：顶栏 `py-2`、ParamSection 头 `py-2.5`、参数行 `py-3`、RunRecordsCard `py-4`。

**为什么是问题**：密集边框 + 无外部间距，会让整页读起来像一张表格而不是几个功能区。用户判断"这属于哪一组"时，缺的不是分隔线而是空间。

**调整**：
- 一级区块之间统一 `mb-6`，区块自身改为带边框的独立容器（`rounded-lg border`）
- 内边距建立两级节奏：**块内行距收紧**（`py-3` → `py-2.5`），**块间距放开**（新增 `mb-6`）

**理由**：行是重复的、密集的、属于同一组；块是稀疏的、不同的、属于不同任务。视觉密度应该跟着信息粒度走。收紧行距 + 放开块距，能形成"密-疏-密-疏"的节奏，比单纯加边框更能让分组被感知。

---

### 2.3 问题 7：滑杆下方的 min/max 数字行是纯噪音（留白）

**现状**：每个滑杆下方固定渲染一行 `min` 和 `max`（`ModelLoadPage.tsx:1432-1435`），例如 `512` 和 `204,800`。

**为什么是问题**：这两个数字对普通用户没有决策价值（不会有人为了看上限是多少去改参数），但每个滑杆占 16px 高 + 一行水平空间。"推理与显存"区 2 个滑块 = 32px 纯噪音。

**调整**：删掉这行，把范围信息并进 `description`（例如「模型最多支持 32768 个 token · 可调范围 512 – 32768」），用 `text-tertiary` 弱化。

**理由**：数字从"占据一个独立视觉单元"降级为"句子的一部分"，注意力权重自然下降，同时信息不丢失。

---

### 2.4 问题 8：ctx 滑杆下方挂了 8 个元素（留白）

**现状**：`SliderParamRow` 的 ticks 渲染成「快速定位」文字标签 + 6 个描边按钮，独立占一行（`:1436-1457`），每个按钮 `px-1.5 py-0.5 text-[10px]`。

**为什么是问题**：ctx 是唯一带 ticks 的滑杆（`:557`），但这 8 个元素把"拖滑杆"这个主要动作挤到了视觉边缘。快速定位和拖滑杆是同一件事的两种方式，不该并列成两个平级控件组。

**调整**：把 tick 改成滑杆轨道正下方的刻度线（贴住轨道，无独立容器、无文字标签），点击刻度即定位；hover 显示完整数值（如 `64K`）。

**理由**：从"控件组"变成"控件的附属标记"，主次立刻分明；同时省下一整行高度。

---

### 2.5 问题 9：两列高度不等导致底部空洞（留白）

**现状**：`<div className="grid items-start lg:grid-cols-2">`（`:546`），左列「推理与显存」5 行、右列「缓存与运行行为」5~6 行（MoE 模型会多出 ncmoe 滑杆）。`items-start` 让两列各自贴顶，短的列底部留下无内容的空白。

**为什么是问题**：两个区块是并列的语义关系（同一层级的两组参数），底部齐平才读得出"这是并排的两组"。不齐的底边会被当成"右边少了一块内容"。

**调整**：让两列行数配平——把「记住加载设置」这类单项开关移出到区块末尾的独立一行；MoE 的 ncmoe 滑杆移到左侧「推理与显存」（它本质是 ngl 的补充，两者在语义上更近）。同时区块改为独立卡片容器，两列不齐时呈现为两张卡片各自到底，空洞变成卡片内留白而非断裂。

**理由**：语义配平优先于数量配平。ncmoe 和 ngl 放一起，用户调 ngl 时能顺手看到 MoE 的 CPU 兜底层数，这本身就是动线优化（见 3.4）。

## 3. 操作动线

### 3.1 目标动线

排障场景的典型闭环是：**换模型 → 调 ctx/ngl → 看显存够不够 → 加载 → 不对就退回上次的配置**。

### 3.2 问题 10：没有「回到上次成功配置」入口（最大缺口）

**现状**：动作组只有 `重置`，语义是**重置为推荐默认值**（`:507` 传 `defaultModelLoadConfig(model)`）。用户想回到"上次能跑的配置"时，唯一办法是打开运行记录，**用肉眼读 `ngl=45 ctx=32768 kv=q8_0` 这串 mono 文本，然后手动一个个填回滑杆**。

**为什么是问题**：这是整个页面最高频的排障动作，而它需要用户手工转录 4 个数字。运行记录里的数据已经是结构化的（`TuneRecord` / `ModelRunRecord`），只是没有变成按钮。

**调整**：在动作组加 `上次成功配置` 按钮，行为是从 `runRecords` 中取最近一条**可信**记录（`kind === 'launch'` 且 `vram_gb != null`，即通过 `plausibleFloor` 检查、未被标记串台的），点击后一次性回填 `ngl / ctx / kv / ncmoe`。

**理由**：把"肉眼转录"变成"一键回填"。数据本来就在内存里的 `runRecords` state 中，实现成本只有一次 `dispatch({ type: 'UPDATE_MODEL_CONFIG' })`，不需要任何后端改动。回填后顶栏显存预测会立即重算，用户立刻能看到"回到上次配置后显存变成多少"。

> 注意：AGENTS.md 要求不静默修改默认参数。这个按钮是**显式点击**才生效，且不改动 `defaultModelLoadConfig`，属于用户主动操作，不违反该约束。

---

### 3.3 问题 11：加载时「停止」按钮让其他按钮重排（可用性缺陷）

**现状**：加载中追加 `停止` 按钮到 `flex-wrap` 尾部（`:1321-1329`），按钮总数 +1 触发换行或位移。

**为什么是问题**：用户点击「加载模型」的瞬间，按钮组重新布局，「加载模型」本身可能被挤到第二行——**刚点下的按钮在手指离开前就移动了**。这是明确的动效缺陷，且发生在最高频的操作上。

**调整**：主行动做成**双态互斥**——空闲态显示「加载模型」，加载态原地替换为「停止加载」（红色 danger 样式）。按钮数量恒定，位置不动。

**理由**：主行动在任一时刻有且只有一个，且它永远在同一像素位置。这同时解决了「主按钮位置漂移」和「停止按钮找不到」两个问题。

---

### 3.4 问题 12：ncmoe 与 ngl 分离（动线）

**现状**：`强制 MoE 权重留在 CPU 的层数` 在右列「缓存与运行行为」里（`:612-623`），而 `GPU 卸载` 在左列「推理与显存」（`:559`）。

**为什么是问题**：调显存时这两个是同一个决策——"多少层放 GPU、多少层留给 CPU"。MoE 模型用户每次都要左右扫视。

**调整**：ncmoe 移到左列，紧跟 ngl 滑杆下方（作为 ngl 的补充项，视觉上从属）。

**理由**：动线优化不只是减少点击，更是减少**视线跳转**。相关参数物理相邻，认知负担下降。

---

### 3.5 问题 13：加载失败要跳页看日志（动线）

**现状**：加载成功后 `SET_VIEW chat`（`:296`）直接离开本页；失败时只在顶栏状态行显示一行 `break-words` 的错误文案（`:1336`），完整细节要去侧栏点「llama 日志」。

**为什么是问题**：
- 失败是排障的**开始**，不是结束。用户在错误文案里看到的往往是后端返回的 title + details，两三行文字塞在一行里 `break-words`，没有代码块、没有等宽、没有可复制性。
- 多跳一次意味着丢失上下文——回到本页还要重新确认刚才的 ctx/ngl 是多少。

**调整**：失败时在参数区顶部内联展开一个错误卡，展示 `title`（半粗体）+ `details`（等宽、可选中文案）+ 「查看完整日志」链接（跳转 llama 日志页）。加载成功后不再强制跳 chat，改为在顶栏显示「已加载 · 前往对话 →」的次级链接，由用户决定去留。

**理由**：失败现场应该在原地处理。但**成功后的自动跳转是有价值的**（多数时候用户就是要开始对话），所以改成"给出入口"而不是"强制执行"——这是两种不同的判断，我倾向于后者，因为它把"加载成功"和"开始对话"解耦，用户可以在成功后继续微调参数再加载。

> 这一条有取舍，如果你更看重"加载完直接开聊"的顺滑感，可以保留自动跳转，只做失败内联。**这一处请你定。**

## 4. 不同屏幕适配

### 4.1 问题 14：主力窗口恰好落在断点盲区（关键缺陷）

**现状**：顶栏横排由容器查询控制（`index.css:445-452`）：

```css
@container (min-width: 1340px) {
  .model-load-summary-row { flex-direction: row; }
  .model-load-summary-metrics { width: 480px; }
}
```

容器是 `.model-load-summary`（`:403` 声明了 `container-type: inline-size`），其宽度 = 窗口宽 − 240（侧栏）− 48（`px-6` 两边）：

| 窗口宽 | 容器宽 | 顶栏形态 |
|---|---|---|
| 1366 | 1078 | **竖排** |
| 1440 | 1152 | **竖排** |
| 1536 | 1248 | **竖排** |
| 1600 | 1312 | **竖排** |
| 1668 | 1380 | 横排 |
| 1920 | 1632 | 横排 |

**为什么是问题**：**横排需要窗口 ≥ 1668px 才触发，而你的主力窗口是 1440~1600。** 也就是说日常使用中顶栏**永远是竖排三段堆叠**——垂直占用约 200px，按钮组被迫换行成两行，主行动「加载模型」落到第二行右端。这是"该突出的没突出"的直接根因，也解释了为什么你觉得动线绕：主按钮不在第一屏的右侧，而在堆叠区域的末尾。

**调整**：pills 从顶栏第 2 段拆出后，第 2 段只剩「预计显存」一个数字，宽度需求从 480px 降到 ~200px。横排断点因此可以下调：

```css
@container (min-width: 1120px) { /* 横排：1440 窗口即可命中 */ }
@container (min-width: 1280px) { /* 指标区加宽到 360px */ }
```

调整后 1440 / 1536 / 1600 三个主力窗口全部命中横排，1366 仍竖排（符合预期）。

---

### 4.2 问题 15：视口断点与容器断点混用（适配一致性）

**现状**：顶栏用 `@container`（容器断点），参数区用 `lg:grid-cols-2`（视口断点 1024px），高级参数折叠区又用 `lg:grid-cols-2`，而侧栏在 959px 切换为图标栏（`ModelWorkspace.tsx:265` `useMediaQuery('(max-width: 959px)')`）。

**为什么是问题**：侧栏存在与否会改变容器宽度，但参数区的 `lg:` 断点只看视口。窗口从 1000px 拖到 950px 时，侧栏从 240px 塌成 56px，容器宽度**反而变宽**（950−56=894 > 1000−240=760），但参数区因为视口跌破 1024 而从两列塌成单列——**容器变宽了，布局却变窄了**。

**调整**：把 `ModelLoadPage` 内所有 `lg:` 视口断点换成同名 `@container` 规则，与顶栏共用一套断点值（1120 / 1280）。页面根容器声明 `container-type: inline-size`。

**理由**：同一条水平线上的内容应当共享断点。这套规则原本是为模型列表页设计的（`.model-list-container`、`.model-toolbar` 已是 container 体系），加载页只是没跟上——统一后侧栏折叠时的布局变化才是单调的。

---

### 4.3 三档适配目标

| 窗口宽 | 容器宽 | 顶栏 | 参数区 |
|---|---|---|---|
| ≥ 1408（容器 ≥1120） | 横排两段：身份+指标 / 动作独占右列 | 两列 |
| 1120 ~ 1408（容器 760~1120） | 顶栏两段式：身份+指标一行，动作下沉一行 | 两列 |
| < 1120（容器 <760） | 竖排三段：身份 / 指标 / 动作 | 单列 |

分档依据：第一档是 1440 及以上的 Windows 常规窗口；第二档覆盖 1366 笔记本与分屏；第三档是侧栏图标化后仍不足的情况。每一档的顶栏动作组都保证主行动独占一行且右对齐。
