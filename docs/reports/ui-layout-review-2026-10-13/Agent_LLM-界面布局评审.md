## 摘要：一个根因解释了大部分「层级乱」

`text-[var(--font-*)]` 这类写法在 Tailwind 里被解析成了**颜色**工具类，**不生成任何字号声明**。实测 Tailwind 编译产物：

```css
.text-\[var\(--font-caption\)\] { color: var(--font-caption); }
.text-\[var\(--font-title\)\]  { color: var(--font-title); }
```

于是这些元素的字号全部回落到继承值（`body` 的 14px）。这类写法在全仓库有 **142 处**，分布在 6 个文件：

| 文件 | 处数 |
| --- | --- |
| `pages/ChatPage.tsx` | 46 |
| `features/apiStatus/ApiStatusPage.tsx` | 36 |
| `features/chat/ChatSidebar.tsx` | 17 |
| `components/ChatBubble.tsx` | 16 |
| `features/apiStatus/ExternalApiSection.tsx` | 14 |
| `components/MarkdownRenderer.tsx` | 13 |

**后果**：设计令牌里定义了 7 档字号（11/12/14/15/16/18/22），凡是经 Tailwind 消费的地方**一档都没生效**；凡是写在 CSS 里消费的地方（`.eyebrow`、`.display-title`、`.prose-body`）**正常生效**。这直接造成「同一套设计系统，一半页面按令牌走、一半页面所有文字都挤在 14px」，也就是你说的主次不分和密度忽松忽紧。

好消息：这个 bug 只吃字号，不动颜色——实测 21 个同时带 `text-[var(--text-*)]` 的元素，文字颜色 **0 处错乱**。

## 一、信息层级

### 1.1 页面主标题在 8 个页面里都只有 14px（P0）

页面主标题由 `PageHeader` 统一提供，而它引用的类从未被定义：

- `app/src/components/PageHeader.tsx:21` → `<h1 className="page-title">`
- `.page-title` 在 `index.css`、`workspace-design.css` 及全仓库 **0 处定义**

**实测**（设置页，1440 宽）：`软件设置` 这个 h1 的计算值是 `font-size: 14px / font-weight: 400`。

同一个页面往下看，区块标题是 `15px / 600`（`.workspace-setting-section h2`）。也就是说：

> 页面标题（14px/400） **比它自己的区块标题（15px/600）更小、更轻。**

**受影响页面**（`PageHeader` 被 11 处引用）：`SettingsPage`、`DataManagementPage`、`KernelUpdatePage`、`ToolsPage`、`UsagePage`、`LogsPage`、`ModelThemePage`、`Fast27bPage`、`EmbeddingWorkspace`、`LlamaLogsPage`、`DshAgentPanel`。

**理由**：一个页面只有一个 H1，它必须明显强于区块标题，否则用户扫视时找不到「我在哪一页」。当前状态下 H1 的字重（400）低于正文强调和所有区块标题（600），视觉上它不是标题，只是一行说明文字。

### 1.2 模型库页的标题被一个不存在的令牌吃掉（P0）

- `app/src/pages/HomePage.tsx:129` 写的是 `text-xl font-bold`（预期 20px/700）
- `app/src/workspace-design.css:7` 用 `font-size: var(--font-page)` 覆盖它，而 `--font-page` **全仓库 0 处定义**（只有这 1 处引用）

**实测**：`模型管理` 这个 h1 的 class 是 `truncate text-xl font-bold`，计算值却是 **14px / 600**。声明失效后 `font-size` 变成 `unset`，直接继承了 body 的 14px。

**理由**：这是「写了 CSS 但变量不存在」的静默失败——代码看起来是有意设计过的，运行时却什么也没发生，排查时最容易漏掉。

### 1.3 对话页标题同样是 14px，且与副标题同号（P1）

- `app/src/pages/ChatPage.tsx:1549` → `text-[var(--font-title)]`（预期 18px）
- 受摘要中那个根因影响，**实测 14px / 600**

**实测**（对话页，1920×1080）页头三行的真实值：

| 元素 | 垂直位置 | 实测字号/字重 |
| --- | --- | --- |
| eyebrow「本地对话 / 主模型」 | y=40–53 | 11px / 700 |
| h1「新对话」 | y=55–76 | **14px / 600** |
| 副标题「未加载模型 · 历史对话可查看」 | y=78–99 | **14px / 400** |

标题和副标题**同为 14px**，只靠字重 600 vs 400 区分——这是层级里最弱的一种区分方式，在中文小字号下几乎看不出差别。

### 1.4 页面主标题目前有 6 种规格（P1）

| 来源 | 字号/字重 |
| --- | --- |
| `PageHeader.tsx:21`（8 个页面） | 14px / 400 |
| `HomePage.tsx:129` | 14px / 600（声明 20px/700，被未定义令牌吃掉） |
| `ChatPage.tsx:1549` | 14px / 600（声明 18px，被 Tailwind 吃成颜色） |
| `SettingsWorkspace.tsx:68` | 16px / 600 |
| `LlamaNativePreviewPage.tsx:230` | 14–15px / 600 |
| `ApiStatusPage.tsx:292`（`.display-title`） | 22px / 700 |

**理由**：同一个角色（页面主标题）跨页面不可比，用户在不同工作区之间切换时会感觉像在用不同的应用。

### 1.5 出现「数字/图标/卡片标题 > 页面标题」的倒挂（P1）

| 场景 | 元素 | 实测 | 被压过的对象 |
| --- | --- | --- | --- |
| 模型库页 | 计数「00」 | **22px** | 页面标题 14px |
| 设置页 | 区块图标 `h-4.5` | **24×24px** | 区块标题 15px |
| API 状态页 | 卡片 h2（`text-[20px]` 写死，生效） | **20px** / 700 | 区块 h2（`text-[var(--font-title)]`，声明 18px，**实际 14px**） |
| 对话页 | 空状态 h2 `.display-title` | 22px / 700 | 页头 h1 14px / 600 |

注意 API 状态页这一行：卡片标题因为写了**硬编码的 `text-[20px]`** 而正常生效，区块标题因为走了**失效的令牌写法**而塌到 14px。同一个页面里「该小的变大了、该大的变小了」，倒挂幅度（20 vs 14）比源码上看起来的（20 vs 18）更严重——这正是 1.0 那个根因最直观的破坏力：**它专门惩罚「用令牌的地方」，奖励「写死的地方」**，于是越规范的代码看起来越乱。

关于图标：`SettingSection.tsx:27`、`McpServersSection.tsx:230`、`ToolsPage.tsx:53/96/137`、`LogsPage.tsx:19` 都用了 `h-4.5 w-4.5`，而 **Tailwind v3.4 的 spacing 刻度里没有 4.5**（有 3.5、没有 4.5），`tailwind.config.js` 也没有扩展。**实测确认**：图标实际渲染为 **24×24px**（lucide 默认值），而不是预期的 18px。

**理由**：图标的视觉重量和它的标题文字直接挂钩。24px 的图标配 15px 的标题，眼睛会先看到图标、再看到文字，层级关系被翻转。

### 1.6 页头三行的间距关系是反的（P1）

- eyebrow 下方：`mb-2` = **8px**（`PageHeader.tsx:17`）
- 主标题下方：`mt-0.5` = 2px，被 `workspace-design.css:5` 覆盖为 **6px**

**理由**：主标题下方的间距（6px）小于上方（8px），意味着主标题在视觉上更靠近它的说明文字、而远离它的上级标签——分组关系被拆错了。正确的关系应该是「eyebrow + 标题」一组、说明另起一组，即上方间距 < 下方间距。

### 1.7 对话页页头把三行文字塞进 60px 且零余量（P1）

`ChatPage.tsx:1544` 的网格是 `grid-rows-[60px_minmax(0,1fr)]`，页头行固定 60px。

**实测**：页头 `clientHeight = 59`、`scrollHeight = 59`、`padding-top/bottom = 0`。内容从 y=40 排到 y=99，即**占满整行，上下余量各 0–1px**。

**理由**：60px 是「一行文字 + 图标按钮」的高度，现在被压进了三行（11px + 14px + 14px）。余量为零意味着任何字号变大、字体回退或系统缩放都会立刻溢出或裁切。

### 1.8 字号口径的实际状况：151 处写死，10–11px 占 84%（P1）

全仓库 `text-[Npx]` 清点：

| 值 | 处数 | 令牌里有对应档位？ |
| --- | --- | --- |
| 9px | 1 | 无 |
| 10px | 33 | 无 |
| 11px | 94 | 有（`--font-eyebrow`） |
| 12px | 1 | 有（`--font-caption`） |
| 13px | 11 | 无 |
| 15px | 8 | 有（`--font-chat`） |
| 17px | 1 | 无 |
| 20px | 2 | 无（接近 `--font-display` 22px） |
| **合计** | **151** | |

**理由**：令牌里最小的档位是 11px，但代码里实际用到了 9px 和 10px（共 34 处）——这些尺寸在令牌体系里**没有合法位置**，只能写死。同时 12px 和 15px 明明有令牌却仍写死。结果是「令牌」和「写死值」两套口径并行，谁改都不会同步。

## 二、区块分布与留白

### 2.1 内容列最大宽度有 8 种口径（P0）

| 最大宽度 | 使用位置 |
| --- | --- |
| `max-w-2xl` = 672px | SettingsPage、DataManagementPage、KernelUpdatePage |
| `max-w-3xl` = 768px | ToolsPage |
| `max-w-4xl` = 896px | Fast27bPage |
| `max-w-5xl` = 1024px | LlamaLogsPage |
| `max-w-[1100px]` | UsagePage |
| `max-w-[1120px]` / 1600px+ → 1360px | ApiStatusPage |
| `max-w-[1180px]` / 1600px+ → 1520px | HomePage、ModelLoadPage、EmbeddingWorkspace |
| 无（撑满） | ChatPage 消息列、ChatSidebar |

**理由**：内容列的宽度决定「一屏能读多少」，是版式节奏的基准线。8 种宽度意味着从设置页切到模型库页时，左边距会从 264px 跳到 320px（同窗口下），视线每次都要重新找起点。

### 2.2 左右内边距有 3 种口径（P1）

- `px-4 sm:px-6`（16 → 24px）：HomePage、ModelLoadPage、Fast27bPage、EmbeddingWorkspace
- `px-6`（固定 24px）：LlamaLogsPage、SettingsPage、UsagePage、ToolsPage、LogsPage、DataManagementPage、KernelUpdatePage
- **0**：`PageLayout.tsx:14`（该组件已无人引用，见 2.9）
- 特例：ChatPage 消息区用 `clamp(18px, 5vw, 72px)`，**实测 1920 宽时为 72px**

**理由**：同为「页面内容距窗口边缘的距离」，在 640px 断点前后会在 16/24px 之间跳一次，而对话页走的是完全不同的 5vw 流式方案。同一窗口宽度下，不同页面的内容起始位置不一致。

### 2.3 侧栏宽度有 3 种口径（P1）

| 侧栏 | 宽度 | 内边距 |
| --- | --- | --- |
| 模型工作区侧栏（`ModelWorkspace.tsx:355`） | `w-60` = **240px** | `p-2` = 8px |
| 模型工作区窄栏（`:274`） | `w-14` = **56px** | `px-1.5` = 6px |
| 对话侧栏（`ChatSidebar.tsx`） | **实测 1920 下 288px**（动态） | `px-2.5` / `px-2` = 10/8px |
| 设置工作区导航（`SettingsWorkspace.tsx:59`） | `w-60` = **240px**（<900px → 208px） | `p-3` = 12px |

**实测对比**：模型库页侧栏 240px / 内边距 8px；对话页侧栏 288px / 内边距 10px。

**理由**：侧栏是全局定位锚点。宽度从 240 跳到 288 意味着主内容区的起点也跟着跳——用户在模型库和对话之间切换时，正文左边缘会横向移动 48px。

### 2.4 设置页的「导航 ↔ 内容」死区随窗口在 56px ↔ 264px 之间漂移（P0）

设置页导航固定 240px，内容列 `max-w-2xl`（672px）在剩余空间里居中：

| 窗口宽度 | 剩余空间 | 内容列左侧死区 |
| --- | --- | --- |
| 1024px | 784px | **56px**（实测内容起始 x≈288） |
| 1440px | 1200px | **264px** |
| 1920px | 1680px | 504px |

**理由**：这是你说的「留白不均」最典型的形态。同一份设置界面，小窗口下导航和内容紧贴，大窗口下中间空出一条比导航本身还宽的空白带。死区本身不承载任何信息，却随窗口放大而放大——用户在宽屏上要横向扫过半个屏幕才能从导航看到内容。

**建议口径**：内容列改为「左对齐 + 最大宽度」而不是「居中 + 最大宽度」，让导航与内容的间距固定（例如 32–48px），多余空间留给右侧。

### 2.5 模型库页在内容出现前先吃掉 203px 垂直空间（P1）

**实测**（1440×900）：

| 区块 | 位置 | 高度 | 内边距 |
| --- | --- | --- | --- |
| 自定义标题栏 | y=0 | 40px | — |
| 页面页头 `.model-library-header` | y=40 | **106px** | 20px / 24px |
| 工具栏 `.model-toolbar` | y=146 | **65px** | 14px / 24px |
| 元信息行 `.model-library-meta` | y=231 | **32px** | 4px / 0 |
| 列表区起点 | y=263 | — | — |

**理由**：900px 高的窗口里，**前 263px（29%）**被「页头 + 工具栏 + 元信息」占掉，真正的内容区只剩 637px。而元信息行的内容是「0 个模型 · 0 个已加载 · 启动桌面版并选择本地 GGUF 模型目录后才会显示真实数据」——在一个空状态的页面上，这 32px 说的是用户已经能从中间那张大卡片上看到的事。

另外页头 106px 里，三行文字（eyebrow 11px + 标题 14px + 说明 12px）实际只占约 45px，其余是 `padding-block: 20px`（被 `workspace-design.css:6` 从 `py-4` 覆盖上来的）。

### 2.6 空态卡片固定 512px，导致三栏步骤在所有宽度下都断行（P1）

`HomePage.tsx:226/280` 的空态卡片被 `workspace-design.css:20` 固定为 `padding: 28px`，宽度上限 `max-w-lg` = **512px**；**实测**（1440）卡片为 `512×330`，位置 `x=584, y=325`。

卡片内的「1. 进入设置 / 2. 添加路径 / 3. 开始加载」是三等分列，每列可用宽度约 **150px**。实测在 **1440 和 1920 两种宽度下都出现同样的断行**：「点击「选择目录」进入设置」被折成两行，第二行只剩一个孤字「置」。

**理由**：卡片宽度固定 → 列宽固定 → 文字断行与窗口大小无关，所以放大窗口并不能改善它。三栏布局在这里也是不必要的：这三步是**线性流程**（先做 1 才能做 2），横排会诱导用户以为它们可以并行。

### 2.7 宽屏下页头两端失去关联（P2）

**实测**（1920）：内容列切到 1520px 后，页面标题「模型管理」在 x≈320，而右侧计数「00」在 x≈1740，两者相距约 **1400px**。

**理由**：「00」这个数字的语义完全依赖「本地模型」这个标签、以及「它是本页模型的计数」这个上下文。当它离标题 1400px 时，用户读到的是一个孤立的数字。

顺带一个内容问题：`HomePage.tsx:135` 用 `padStart(2,'0')` 格式化，0 个模型时渲染出来是 **「00」**——空状态下的两位零看起来像渲染错误或未初始化的占位符。

### 2.8 区块垂直节奏有 4 种，标题→内容间距有 5 种（P1）

| 角色 | 数值 | 出处 |
| --- | --- | --- |
| 区块容器 padding-block | **24px** | `workspace-design.css:21`（`.workspace-setting-section`，实测确认） |
| 同上 | 20px | `ToolsPage.tsx:49`、`McpServersSection.tsx:226`、`UsagePage.tsx:148` |
| 同上 | 16px | `LogsPage.tsx:17` |
| 同上 | 无（用 `mt-7`=28px） | `ApiStatusPage.tsx:79` |
| 区块标题→内容 | **18px** | `workspace-design.css:22`（覆盖 `mb-3`） |
| 同上 | 8px | `ToolsPage.tsx:52`、`McpServersSection.tsx:229` |
| 同上 | 12px | `ApiStatusPage.tsx:80` |
| 同上 | 16px | `LogsPage.tsx:18` |
| 同上 | 20px | `UsagePage.tsx:149/215` |

**理由**：`workspace-design.css` 里的两条全局覆盖规则（24px / 18px）只作用于带 `.workspace-setting-section` 的区块，其他页面各写各的。于是「区块之间隔多远」这件事在同一应用里有 4 个答案，「标题和内容贴多近」有 5 个答案。用户翻页时会感觉疏密节奏在变。

### 2.9 对话页为输入框预留 205px，短会话时中间是大片空白（P2）

**实测**（对话页 1920×1080）：消息滚动区 `padding: 72px 72px 28px 205px`（`clamp(138px,19vh,208px)` 在 1080 高时取 205px）。

**理由**：这 205px 是为了让最后一条消息不被悬浮输入框盖住而预留的。但在空会话或短会话时（见 `shot-02-chat-1440.png`），它表现为空状态卡片和输入框之间一条约 200px 的空白带。更精确的做法是只在滚动到底部时预留，或用 `scroll-padding-bottom` 交给浏览器处理。

### 2.10 顺带发现：`PageLayout` 是死代码，且引用的类也不存在（P2）

- `app/src/components/PageLayout.tsx:13/14/17` 引用 `.page-layout`、`.page-band`，两者**全仓库 0 处定义**
- `PageLayout` 本身**没有任何页面 import**（仅自身文件与 `docs/plans/UI_REDESIGN_ACCEPTANCE.md` 提及）

**理由**：与 1.1、1.2 是同一类问题（引用了不存在的 CSS 类）。`PageHeader` 被 11 处引用、后果严重；`PageLayout` 已无人使用，可以直接删除，避免以后有人误用。

## 三、操作动线

### 3.1 首次使用的核心动作被拆成两条路径、3–4 步（P0）

目标：让应用找到本地 GGUF 模型目录。

| 路径 | 步骤 |
| --- | --- |
| A（空态卡片） | 模型库页 → 点卡片内「选择目录」 → 进入设置 → 选目录 → 回首页 |
| B（侧栏） | 模型库页 → 侧栏底部「软件设置」 → 设置页 → 侧栏「本地模型运行」 → 「模型目录」行 → 「选择目录」 |

**理由**：这是新用户唯一的必经动作（没有模型目录，整个应用不可用），却既没有唯一入口、也没有最短路径。空态卡片写着「回到首页即可直接加载」，说明作者知道这里需要往返——而往返本身是不必要的，目录选择完全可以在模型库页就地完成。

### 3.2 空态文案与按钮名称、实际行为三者不一致（P1）

- 空态说明（`HomePage.tsx:189`）：「或点击上方「**下载**」面板在线拉取模型」——暗示应用内有个「下载」面板
- 工具栏实际按钮名：**「魔搭下载」**（快照实测的无障碍名称）
- 实际行为（`HomePage.tsx:166-169`）：`openExternalUrl(MODEL_SCOPE_URL)`，`title="在浏览器中打开魔搭模型库"`——**跳到外部浏览器**，不是应用内面板

**理由**：文案承诺了一个「面板」，用户点下去得到的是浏览器跳转。同一个动作在说明里叫「下载」、在按钮上叫「魔搭下载」、在行为上是「打开网页」，三个名字对不上，用户无法建立稳定的预期。这是动线里最容易修、也最容易让人困惑的一处。

### 3.3 进入设置与退出设置的位置不对称（P1）

- **进入**：模型工作区侧栏**底部**的「软件设置」
- **退出**：设置页内容区**左上角**的返回箭头

**理由**：进出同一个工作区的控件分处两个对角，用户每次都要重新定位。对称的做法是「入口在哪，出口就在哪」（侧栏底部进入 → 侧栏顶部或同一位置返回）。

### 3.4 「新建对话」类动作在不同工作区的位置不一致（P2）

- 对话侧栏：**顶部**第一项「新建对话」
- 模型工作区侧栏：**底部**的「切换到对话 / 尚未选择模型」

**理由**：都属于「开始一次对话」，一个在列表首屏、一个在屏幕最底部。而且底部那个还带状态副标题（「尚未选择模型」），把导航动作和状态提示混在了同一个控件里。

### 3.5 模型库页顶栏把 6 个不同性质的控件排成同级（P2）

同一行内：搜索框、刷新列表、默认排序、单列、多列、魔搭下载。

**理由**：这 6 个控件分属四类——检索（搜索）、数据操作（刷新）、排序（默认排序）、视图偏好（单列/多列）、外部导航（魔搭下载）。其中「单列/多列」是纯视图切换（可持久化偏好），却与「魔搭下载」（会离开应用）占用同等视觉权重。建议按性质分组：检索独立一行或左对齐，视图偏好收进一个分段控件，外部导航降为次要按钮。

### 3.6 对话输入区的工具行一行放了 8 个元素（P2）

**实测截图**（`shot-02-chat-1440.png`）底部输入卡内：左侧「+ / 自动 / 模型默认 / 麦克风 / 删除」，右侧「Enter 发送，Shift + Enter 换行」+ 圆形发送键。

**理由**：键盘提示属于「首次使用的辅助信息」，长期用户不需要；它和工具按钮同处一行、同为小字，视觉权重相同。建议键盘提示在首次使用后淡出，或移到输入框的 placeholder 位置。

## 四、屏幕适配

### 4.1 默认窗口 1200×780，内容区实际只有 960px（P0）

`src-tauri/tauri.conf.json`：`width: 1200`、`height: 780`、`minWidth: 800`、`minHeight: 600`、`resizable: true`。

减去 240px 侧栏，**默认窗口下主内容区只有 960px 宽**。

### 4.2 模型加载页的顶栏在默认窗口下永远是竖排（P0，推算）

`index.css:445` 定义：

```css
@container (min-width: 1340px) { .model-load-summary-row { flex-direction: row; ... } }
```

这是**容器查询**，阈值 1340px 指的是容器自身宽度（`.model-load-summary` 声明了 `container-type: inline-size`）。容器宽度 ≈ 窗口宽 − 240px 侧栏，因此：

- 默认窗口 1200px → 容器 960px → **不满足 1340px，顶栏保持竖排**
- 需要窗口宽度 ≥ **1580px** 才会切到横排（`index.css:450` 的 1460px 断点则需 ≥1700px）

**理由**：设计者显然是在宽屏（1600px+）上调试的，但这个应用的默认窗口是 1200px——**绝大多数用户第一次打开时看到的都是竖排版本**，横排布局只有手动最大化到宽屏才能看到。这不是「响应式做得好不好」的问题，而是断点与默认窗口尺寸不匹配：花了力气做的横排布局，在默认状态下永远不会出现。

> 此项为**推算**：容器宽度按 `窗口宽 − 240px` 计算，未在真实模型加载态截图核对（需要先加载模型才能进入该页面）。

### 4.3 内容列在 1600px 处一次性跳宽 340px（P1）

`min-[1600px]:max-w-[1520px]`：内容列在 1599px 时是 1180px，1600px 时突变为 1520px。

**理由**：340px 的突变会让所有依赖这个宽度的子布局（网格列数、卡片宽度、空态卡片位置）同时跳一下。**实测**：1920 下内容列起点 x≈320，而 1440 下为 x≈264。如果这是有意的设计意图，建议改成平滑的 `clamp()`；如果只是为了在超宽屏上「填满」，则应该由内容本身决定（网格自适应），而不是由容器宽度硬切。

### 4.4 窗口 < 640px 时计数信息直接消失（P1）

`workspace-design.css:26`：

```css
@media (max-width: 640px) { .model-library-count { display: none; } }
```

**理由**：模型数量是这个页面的核心信息之一。窄窗口下直接 `display: none` 属于「信息删除」，而正确做法是**重排**（例如把计数移进标题行、或缩为标题旁的一个小徽标）。这个应用的 `minWidth` 是 800px，所以这条规则在桌面端实际不可达——但它同样会命中**浏览器的窄视口**（例如分屏、移动端远程访问），那时信息会无声消失。

### 4.5 900px 宽时侧栏折叠，但空态卡片不跟着变（P1）

**实测**（`shot-05-model-900.png`）：900px 宽时模型侧栏自动折叠为 56px 图标栏，主内容区变宽到约 844px。但空态卡片仍固定 512px，三栏步骤的文字依旧断行出现孤字。

**理由**：侧栏已经让出了 184px 的空间，这部分空间没有回流到内容布局里——卡片宽度写死，宽度变化被浪费了。

### 4.6 对话页的流式内边距与固定消息列宽不匹配（P2）

- 消息区左右内边距：`clamp(18px, 5vw, 72px)` → **实测 1920 下 72px**，900 下约 45px
- 消息列与输入框宽度：768px（1600px+ → 896px）**固定**
- 对话侧栏宽度：动态（实测 1920 下 288px）

**理由**：三个宽度参数用了三种不同的响应策略（流式 / 固定 / 动态）。在窄窗口下，侧栏 + 固定 768px 消息列 + 流式内边距会互相挤压，消息列的实际可用宽度取决于三者中最紧的那个。建议消息列也用 `min()` 约束（如 `min(768px, 100% - 2*内边距)`），让三者有一致的收敛方向。

## 五、建议的收敛口径（不含代码改动）

按「一处根因影响多大」排序。

### P0-1　修复令牌消费方式（一行改法，影响 142 处）

Tailwind 对 `text-[...]` 的任意值存在**类型歧义**（可能是 font-size，也可能是 color），必须加类型提示：

```
text-[var(--font-title)]        →  text-[length:var(--font-title)]
```

**验收方法**：改完后在浏览器里查 `.text-\[var\(--font-title\)\]` 这条规则，应该是 `font-size: var(--font-title)` 而不是 `color: ...`；对话页 h1 的计算字号应从 14px 变为 18px。

### P0-2　补齐 3 个缺失定义（或删掉引用）

| 缺失对象 | 引用位置 | 处理建议 |
| --- | --- | --- |
| `.page-title` | `PageHeader.tsx:21`（11 处引用） | 定义它（例如 `font-size: var(--font-title); font-weight: 600;`），或直接把令牌类写进 JSX |
| `--font-page` | `workspace-design.css:7` | 定义令牌，或改用已有的 `--font-title` / `--font-display` |
| `.page-layout` / `.page-band` | `PageLayout.tsx`（0 处引用） | 直接删除该组件 |

### P0-3　确认断点与默认窗口的关系

把 `index.css:445` 的 `1340px` 容器断点与「默认窗口 1200px / 侧栏 240px」放在一起复核：要么降低阈值到默认窗口也能触发，要么调整默认窗口宽度，要么承认横排只服务于宽屏并显式设计竖排版本。

### P1-1　字号收口为 5 档

现有令牌 7 档偏多，且写死值里有 9/10/13/17/20px 五个「无令牌可归」的尺寸。建议收敛为：

| 档位 | 用途 | 现状来源 |
| --- | --- | --- |
| 11px | eyebrow / 徽标 / 元信息 | `--font-eyebrow`（已有，但 94 处写死） |
| 13px | 辅助说明 / 紧凑标签 | 新增（吸收现有 9/10/13px 共 45 处） |
| 14px | 正文 / 列表项 / 表单 | `--font-body`（已有） |
| 16px | 区块标题 | 吸收现有 15px（8 处）与 16px |
| 20px | 页面主标题 | 吸收现有 18/20/22px 三种主标题 |

同时删掉 9px 与 10px 两档（共 34 处）——中文在 10px 下可读性已经不足，这与无障碍下限也冲突。

### P1-2　间距收口为 4 档

针对 2.8 的 4 种 padding 与 5 种标题间距，建议统一为：区块 padding-block 用 24px、标题→内容用 12px（比现在的 18px 紧）、区块之间用 0（靠 border 分隔）、页头→内容用 24px。**关键是把 `workspace-design.css` 里那两条全局覆盖规则变成唯一口径**，其他页面不再各写各的。

### P1-3　内容列与左右内边距统一

8 种内容列宽收敛为 2 种：**阅读型页面**（设置、工具、日志、数据管理）统一 720–768px；**工作台型页面**（模型库、加载页、用量）统一 1180–1280px。左右内边距统一为 24px（去掉 `sm:` 断点跳变），对话页的 5vw 保留但要与消息列宽联动（见 4.6）。

### P1-4　侧栏宽度统一

模型工作区 240px 与对话侧栏 288px 收敛为同一值（建议 240px），内边距统一 8–12px。侧栏是全局锚点，宽度跳变会带动所有页面的正文左边缘移动。

### P2-1　空态卡片改为单列步骤

把 2.6 的三栏步骤改成竖向单列（左编号 + 右文案），并把卡片宽度从固定 512px 改为 `min(512px, 100% - 48px)`。理由见 2.6：这三步是线性流程，横排既不真实也会断行。

### P2-2　修 3.1 的动线

给「选择本地模型目录」一个唯一入口，并允许在模型库页就地完成（不必跳设置页）。若必须跳转，则空态卡片的「选择目录」按钮应直接落在设置页的对应区块上，而不是落在设置页首屏。

### P2-3　修 3.2 的文案一致性

统一叫法：按钮名 = 说明里的名字 = 行为描述。若行为是打开外部浏览器，按钮就不该叫「下载」，文案也不该说「面板」。
