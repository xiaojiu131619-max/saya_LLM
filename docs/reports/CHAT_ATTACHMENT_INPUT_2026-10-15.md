# 聊天粘贴与跨应用拖放接入

## 已实现

- 聊天输入框接收用户主动粘贴的图片与文件；`clipboardData.files` 和 `items.getAsFile()` 共用既有附件校验、读取及发送链路。主模型与 fast-27b 共用入口，后端原有能力约束保留。
- Windows 桌面窗口的 `dragDropEnabled` 关闭，避免 Tauri 原生只提供本地路径的接管阻断 WebView2 的 HTML5 拖放。聊天拖放统一接收浏览器提供的 `File`，不再依赖原生窗口文件监听或可选的 `File.path`。
- 支持跨应用提供的真实文件、图片文件、HTML 中内嵌的常见位图 base64 数据、纯文字、HTML 文字及 URI 列表。链接只作为文字，不当作文件内容读取。
- 单次事件内优先实际文件，对 `files` 与 `items` 去重，避免重复附件；实际文件所附带的文件名或本地路径文字不自动加入消息。
- 普通文字粘贴不拦截，保留原生选区、撤销与输入法行为。输入框内部拖动选中文字也交还浏览器，避免将文字重复追加到末尾。
- 图片/富文本粘贴和外来拖放在事件结束前同步提取数据，随后再异步读取文件。生成中拒绝新增附件；读取中阻止发送与编辑重发，发送按钮提供读取提示。
- 未启动模型时可以先准备文字和附件，发送仍要求后端可用，不会因此启动或切换引擎。
- 关闭原生拖放后，应用级保留 Files、URI、HTML 的默认导航保护，其他页面拖入内容不会直接替换应用页面。

## 保留的限制

- 跨应用兼容性取决于来源应用和 WebView2 是否暴露可读取的文件/图片数据，不能保证所有软件或所有拖放格式。
- 微信、QQ、邮件客户端等应用若只给出私有对象、`FILEDESCRIPTOR/FILECONTENTS` 虚拟文件或无法读取的文件描述，当前不新增原生流桥接。对于有事件但没有可读文件的数据给出“先保存到本机再添加”的提示；源应用完全不产生 WebView 可接收的事件时，前端无法提示。
- 网页图片若只提供 HTTP(S)、blob 或 file 链接，不下载、不通过 Rust 读取对应路径、不自动联网。HTML 图片给出复制图片本身/截图/保存文件的提示；仅 URI 列表可作为文字加入消息。
- HTML 使用惰性 `template` 解析，只提取图片数据和纯文字，不插入可见 DOM，不执行脚本或加载资源。
- 不增加 PDF、Word 等文档解析；文本附件仍限 1 MiB，单媒体仍限 80 MiB；内嵌图片限制为常见位图 MIME，不接受 SVG。
- fast-27b 仍不接受音频，视频只理解画面；不修改任何加载或推理参数，不修改显存预测。
